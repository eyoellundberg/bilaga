# Bilaga security and performance review

Reviewed 8 September 2026. Scope: the controlled, single-token file-transfer prototype. This is a code and configuration review with regression tests, not an independent penetration test or certification of OWASP ASVS compliance.

## Stack

TypeScript strict mode, React 19.2.8, Tailwind CSS 4.2.1, Vinext 1.0.0-beta.9, and Vite 8.2.2. Hosted execution uses a Cloudflare Worker, D1 for transfer metadata, and private R2 object storage through Sites. Vinext remains a beta framework. Billing and Google identity are not implemented.

## Controls checked and strengthened

| Area | Implementation and verification |
|---|---|
| Upload authorization | A strong random test token is checked against a server-side SHA-256 digest. Token comparisons inspect the whole digest. Management queries bind the authenticated owner and transfer ID. No account-deletion API exists. Production needs account identity and separately revocable scoped keys. |
| Data separation | Public link IDs differ from private transfer IDs. Stored object keys are generated by the server. No bucket listing or direct public R2 access is exposed by the app. Recipients are authorized by possession of an unguessable link. |
| Resource consumption | Atomic D1 reservation enforces 100 new sessions/day, three unfinished uploads, and 10 GB reserved storage per token before allocating R2 storage. Tests issue ten simultaneous creations and verify exactly three succeed. Request limits are persisted: 300 authenticated requests/minute per token and 120 download requests/minute per link. |
| Body and memory bounds | JSON bodies are capped at 4 KiB; binary parts at 8 MiB; whole files at 1 decimal GB. Bodies have a 30-second read deadline. A per-isolate counter admits at most two simultaneous buffered chunk requests. Input is copied into one preallocated buffer instead of accumulating and concatenating chunks. |
| Upload consistency | Each part is reserved with a SHA-256 identity. Matching retries are idempotent; different bytes for the same part are rejected. Completion checks part count, recorded sizes, ETags, and final R2 size. Completion uses a recoverable lease; an older failed attempt cannot reset a newer lease. Concurrent completion preserves one link and expiry. |
| Deletion and expiry | Link access is checked on every download, including after the R2 lookup when recording a GET. Deletion revokes and redacts first. An unsuccessful purge remains queued separately from the deleted status. Concurrent deletion wins against completion; tests cover that race. New downloads stop at expiry; in-progress downloads may finish. |
| Injection and file handling | SQL values use prepared bindings. Filenames have length/control-character/path-separator checks, and reserved names are rejected. React renders untrusted metadata as text. Downloads are forced to application/octet-stream attachments, with nosniff, sandbox CSP, and no-store. Files are not parsed, rendered, decompressed, or executed by Bilaga. |
| Browser boundaries | HTML uses a fresh script nonce per response, strict-dynamic, disabled inline script attributes, restricted origins, no framing/objects/base URLs, a permissions policy, and production HSTS. Tests verify nonce freshness and reject caller-controlled nonce selection. Inline styles remain allowed because the current component library uses them. |
| Unused attack surface | React Server Action requests and non-API mutations are rejected. The unused image optimization route is disabled. Cross-origin browser mutations and compressed HTTP request bodies are rejected. There is no server-side URL-fetch/upload feature, reducing SSRF exposure. |
| Secrets and errors | Tokens stay out of URLs, client bundles, source control, and logs. Built output was scanned for both the local token and its configured digest; neither appeared. API error messages are bounded and omit internal storage/database details. |

## Dependencies

The initial audit reported five high-severity production dependency entries. Compatible patches were applied to React Server Components, Vinext, Vite, Cloudflare tooling, and their dependencies. The production audit then reported **zero known vulnerabilities**. A refreshed full audit reports **four moderate development-only entries**, all arising from the old esbuild dependency used by Drizzle's configuration loader (`esbuild`, `@esbuild-kit/core-utils`, `@esbuild-kit/esm-loader`, and `drizzle-kit`). The suggested automatic fix would downgrade Drizzle across a breaking version boundary; that was not applied. These packages are not shipped in the Worker bundle, and this project does not run an esbuild development server. Track an upstream compatible fix. A clean production audit is not proof that vulnerabilities are absent.

## Verification

The 37-request local integration suite passed against actual local Worker, D1, and R2 bindings. It checks multipart bytes, retries, authentication failures, completion idempotency, byte ranges, download accounting, deletion, forced expiry, and cleanup. A separate security suite passed origin/encoding/body rejection, CSP nonce freshness and propagation, Server Action rejection, concurrent creation quotas, immutable parts, attachment/sandbox headers, concurrent completion, deletion versus completion, purge retry eligibility, storage quotas, and rate limiting.

Strict TypeScript checking and the production build passed. A browser read/render check of the hardened local home page showed no browser errors. The earlier live API test uploaded a synthetic file and downloaded identical bytes without recipient sign-in. Browser upload was not completed after permission was declined, and the browser automation did not confirm the download-button event; no claim of a fully verified browser upload/download journey is made. WebMCP registration was observed, but its successful current-transfer execution remains unverified. The API does not depend on WebMCP.

## Performance measurements

Compared with the previously published v2 artifact, generated CSS fell from 382,786 to 29,652 bytes uncompressed, and from 57,978 to 6,376 bytes under the same gzip calculation: approximately **89% less compressed CSS**. Tailwind now scans the app and the three UI primitives actually used, rather than the entire bundled component catalog. All emitted JavaScript totals approximately 144 KB gzipped; this is a build-artifact total, not a measured first-load network budget. No Lighthouse/Core Web Vitals or production load-test claims are made.

File downloads stream from R2 with byte-range support. Upload memory scales with the bounded chunks in flight, not the full file size. Database queries are indexed for owner/history, expiry, and rate-limit cleanup. No third-party fonts, analytics, image assets, or email delivery dependency were added.

## Remaining before unrestricted public use

The private upload token is intentionally a prototype identity system. Public enrollment requires Google authentication, individual token revocation/scopes, and account-level ownership checks tested across multiple identities. Stripe payments need an idempotent payment-confirmation flow and transactional balance reservations; there is no billing to audit yet.

A scheduled storage purge and an R2 lifecycle rule for abandoned multipart uploads are still required. Current cleanup runs on new-transfer activity or the authenticated cleanup endpoint, so inaccessible bytes can remain longer than seven days while idle. A storage creation request whose response is lost before its multipart ID is recorded may require the bucket lifecycle rule to reclaim it.

Uploaded files are deliberately opaque and no file-type allowlist, signature inspection, antivirus, or content-disarm service is enabled. This keeps the server from parsing arbitrary formats, but it does **not** make downloaded files safe to open. Public launch needs a defined content/abuse response and scanning/quarantine policy. Password-protected archives also require an explicit policy; scanning cannot guarantee their contents are safe.

Per-transfer/API limits do not replace edge-level DDoS and global cost controls. Review those on the eventual hosting account, along with storage budgets, monitoring, recovery/backups, and administrative access. Formal ASVS assessment, sustained load testing, and an independent review remain separate work.
